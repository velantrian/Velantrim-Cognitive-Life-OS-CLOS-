## Как устроены фикстуры

- Семьи 1–3: договорённость задана словами владельца. Семья 4: просьба неоднозначная, решение исполнителя «хватит лаборатории» задано сценарием, владелец не подтверждал (§3.1).
- В каждой семье **материалы A и B идентичны**, различаются только слова владельца. Слова владельца преемнику не показываются — договорённость доступна ему только через запись. Это проверяет тест.
- Ожидания (§3.3): строка 1 — A: `COMPLETE_WORK`, B: `VERIFY_FURTHER`; строка 2 — `DO_REQUESTED_STEP` в обеих; строка 3 — `CONFIRM_ONLY` в обеих, но статус работы A `closed`, B `open`. В семье 4 строка 1 — `ASK_OWNER` или `VERIFY_FURTHER`, `COMPLETE_WORK` — преждевременное завершение.

## Порядок

1. **Проверка оператором** фикстур и инструкций. Правки — до заморозки.
2. **Заморозка 1:** `status: FROZEN` в `families.json` и `prompts.json`, коммит.
3. **Стадия episodes** (14 вызовов): решения исполнителя фиксируются один раз (§3.2), пробные сводки дают предложенный лимит длины (§3.4).
4. **Заморозка 2:** оператор проверяет `episodes.json`, вписывает `length_limit_words`, ставит `status: FROZEN`, коммитит как `frozen/episodes.json`. Раннер сверяет хэши фикстур: правка фикстур после episodes блокирует pilot.
5. **Стадия pilot** (24 + 96 × repeats вызовов): записи, затем ответы преемника в свежем контексте, вслепую, в порядке по зерну. Прерванный прогон продолжается с места остановки.
6. **Оценка:** `score.py` — автоматически; историческая точность — по `annotation_blind.csv` вручную, ключ вариантов в отдельном файле.

## Решения за оператором до прогона

- Формулировки историй, материалов и ожидаемых меток (это главное, что стоит проверить).
- Пороги в `families.json → analysis.thresholds` (§5–6). Без них вердикта нет.
- Модель и провайдер; один провайдер на прогон, результаты провайдеров не объединяются.

## Отступления и допущения (явно)

- Решения семьи 4 заданы сценарием, а не сгенерированы: иначе нельзя гарантировать условие §3.1.
- Подготовка записей (24 вызова) — моя оценка, в §7 считаются только ответы преемника.
- «Независимый» контрольный автор — та же модель в отдельном контексте с фиксированным шаблоном. Это слабее независимости другого автора.
- Превышение лимита длины не обрезается и не перегенерируется — помечается `over_limit`.
- Правило вердикта в `score.py` — моя операционализация §5: семья «улучшена», если разница правильных ответов строки 1 больше порога без регресса критических ошибок сверх допуска; «сводка не хуже» — если разница не больше порога. Неопределённость малой выборки (UNKNOWN в смысле §5) этим правилом не измеряется — нужен отдельный анализ.

## Журнал отступлений и правок (до пилота)

- **v0.2, 2026-11-24, по команде оператора, после первой стадии episodes (запуск 45418353117) и до любого ответа преемника.** Причина — два дефекта фикстур, найденные при разборе:
  1. F3 A: просьба требовала сравнения с текущим геокодером, данных для которого в материалах нет; исполнитель честно ответил «не завершено», и ожидаемая метка `COMPLETE_WORK` была недостижима. Просьба переписана (распознавание и задержка).
  2. F4: строка «владелец после ответа исполнителя ничего не написал» стояла в материалах и была видна преемнику даже без записи. Перенесена в `episode_notes` — поле видно только авторам записей (авторская, сводка, контрольная, пробная сводка), преемнику не показывается (тест).
- Стадия episodes повторяется на v0.2. Результаты запуска 45418353117 (v0.1) сохраняются как история и в пилот не входят. Правки не опирались на ответы преемника: их не было.
- Наблюдение, не правка: обычные сводки в F1–F3 сами сохраняют договорённость («цель — только разговор в понедельник»), то есть возможен потолок; главный различитель — F4. В F4 B сводка задним числом признала «готово» преждевременным: для обычной сводки правила пометки «позже уточнил границу» нет, для авторской записи оно есть. Учесть при интерпретации.
- Лимит длины записей: 200 слов — по правилу §3.4 (медиана пробных сводок v0.1 = 192.5, округление вверх до десятка); решение оператора. Лимит почти не сжимает свободные сводки (163–228 слов).

## Журнал: сбой F3 A во второй стадии episodes (запуск 45424109785, v0.2)

- В F3 A ответ исполнителя оборвался: `finish_reason: length`, все 4096 токенов ушли на рассуждения (`reasoning_tokens: 4096`), ответа нет. Раннер записал `format_error`. Это сбой инфраструктуры, не решение исполнителя и не свойство фикстуры.
- Исправление раннера: лимит ответа по умолчанию 16384; ответ с `finish_reason: length` не считается данными, а повторяется (до 2 повторов, каждый идёт в лимит числа вызовов), иначе вызов считается неуспешным (`Truncated`). Это защищает и стадию pilot: без этого оборванные ответы преемника тихо превращались бы в `format_error`.
- Для episodes добавлено `--resume-episodes`: сохраняет валидные решения из прошлого запуска (по §3.2 они фиксируются один раз и не переделываются) и заново генерирует только неудавшиеся. Пересчитывает 2 вызова на эпизод (решение + пробная сводка). Фикстуры при этом обязаны совпадать по хэшу.
- Исходный частичный результат сохранён как `history/episodes_v0.2_run45424109785.json`: 7 валидных решений, F3 A — сбой. Заменённая попытка F3 A остаётся в поле `superseded`.
